# pre-release-check

Run the full release gate before cutting a release. All checks must pass
before tagging.

## Steps

### 1. Run the component skills

Run each skill in order and collect its result (PASS or FAIL with
details):

1. **check-licenses** -- must run first because a license failure is the
   most fundamental blocker.
2. **check-dependencies** -- advisories, funding, and the 14-day rule on any
   version taken. Runs early: an update it recommends changes what everything
   below is testing, so taking one afterwards invalidates the whole gate.
3. **run-tests-and-linters** -- lint, typecheck, and coverage at 90%.
4. **check-fixtures** -- drive the built binary against `fixtures/` end to
   end. This is the only check that exercises the real binary against real
   files, so it catches wiring regressions the unit tests (which run
   against in-memory fakes) cannot see. Six of the twelve specs need a real
   `whisper-cli` binary and model file; on a machine without them, those
   six fail loudly naming the missing binary, and that is environmental,
   not a release blocker on its own -- attribute every failure (missing
   whisper-cli, fixture drift, product change, harness defect) before
   deciding whether it blocks.
5. **check-docs** -- README.md, cross-references, command accuracy,
   version references.
6. **check-changes** -- CHANGES.md Development section vs. commit history.

If check-licenses, check-dependencies or run-tests-and-linters fails, report
the failure and stop. A `--prod` advisory or a version younger than 14 days
blocks a release: the first ships a known vulnerability, and the second ships
a version nobody has had time to find one in. If check-fixtures fails for a reason other than the missing
`whisper-cli` binary (fixture drift, a product change, or a harness
defect), treat it the same way -- a release must not ship while tests,
licenses, or the end-to-end run are failing for a reason within this
project's control. The remaining checks can still be reported for
completeness.

### 2. Verify the version bump

- Read `version` from the root `package.json`.
- Confirm the same version appears in `packages/core/package.json`,
  `packages/providers/package.json`, and `apps/cli/package.json`.
- Confirm `CHANGES.md` has a `## Version <X.Y.Z>` section that matches the
  version in `package.json`, OR that the developer has prepared the entry
  under `## Development` and it is ready to be promoted by `bump-version`.
- If versions are inconsistent across packages, list the discrepancies.

### 3. Verify the tag will be accepted from this branch

```bash
git branch --show-current
```

A release candidate (`v<version>-rc.<n>`) is cut from `develop`; a final
release (`v<version>`) is cut from `main`. Only RC tags may come from
`develop`.

If the intended tag is final and the current branch is `develop`, the
release is not ready: merge to `main` first, or cut an RC instead.

### 4. Verify conventional-commits format for commits since the last release

```bash
git log --oneline <last-release-boundary>..HEAD
```

For each commit subject, verify:

- Starts with a valid type prefix: `feat`, `fix`, `chore`, `docs`, `test`,
  `refactor`, `perf`, `ci`, or `build`, optionally followed by `(scope)`
  and a colon. (The release commit itself is `chore: release <version>`,
  not a bare `release:` prefix -- `release` is not one of this project's
  Conventional Commits types.)
- Subject is under 72 characters.
- Contains no AI-tool mentions (no `Co-Authored-By: Claude`,
  `Co-Authored-By: Codex`, "generated by", "with the help of AI", or
  similar).

Report each non-conforming commit with its hash and the specific
violation.

### 5. Report

Produce a release-readiness summary:

```
check-licenses:            PASS / FAIL
check-dependencies:        PASS / FAIL (advisories: prod / dev only; ages: ok / N too young)
run-tests-and-linters:     PASS / FAIL
check-fixtures:            PASS / FAIL (attribute: missing whisper-cli / fixture drift / product change / harness defect)
check-docs:                PASS / FAIL
check-changes:             PASS / FAIL
tag provenance (branch):   PASS / FAIL
version bump consistent:   PASS / FAIL
conventional commits:      PASS / FAIL (N non-conforming commits)

Release gate: PASS / FAIL
```

If the gate is PASS, confirm: "All checks passed. The release may
proceed." If the gate is FAIL, list every blocking issue with enough
detail for the developer to act immediately. Do not tag or publish a
release while any required check is failing.
